# Replay model

Replay turns upstream source commits into destination commits. It is the part of
the engine that decides what published history looks like, so its rules are
stated in terms of what may never happen: a published tag never moves, a
consumer branch never rewinds, and history generated under one profile is never
regenerated under another.

## Profile epochs

A profile epoch is one run of replay under one profile hash. It is represented
by exactly two values: the hash, and the destination commit the epoch grafts
onto.

The hash is `sha256:` followed by 64 lowercase hex characters. It is computed
over a length-framed identity containing the released engine version and an
explicit allowlist of the output-affecting profile fields, YAML-encoded
canonically. The allowlist is a positive list rather than a subtraction, so a
field added to the schema does not silently join the hash. What is in and out is
listed in [config-reference.md](config-reference.md#what-feeds-the-profile-hash).

Observational settings stay out because they cannot change a generated byte.
Closure limits and the closure golden gate publication; they do not alter it.
`determinism.chunkSize` decides how a long backfill is divided, not what it
produces.

A control-plane change — a new prune entry, a patch, a type policy decision, a
different engine or toolchain — produces a different hash and therefore a new
epoch. A new epoch starts on the current destination branch. Older tags are
never regenerated under it. This is the rule that makes the immutability of
published tags survive the engine changing.

### Operator control-plane commits

The consumer branch also carries setup-owned files such as `soapbox.yaml`, the
nested engine shim, and workflows. Human-signed upgrades to those files are not
images of a Kubernetes source commit, so state deliberately continues to record
the last generated commit while the remote branch may fast-forward above it.

Discovery accepts that split only after proving the remote head descends from the
recorded generated object through a linear chain, every intervening commit lacks
the configured source-provenance trailer, and every changed path is
operator-owned. Any change to `go.mod`, `go.sum`, generated facade/provenance
files, or `destination.internalPrefix` is fatal. The verified remote head becomes
the graft point of the next profile epoch; the source cursor continues from the
generated base. This preserves control-plane upgrades without falsely mapping one
source commit to two destination commits.

## The mapping

Each source commit maps to at most one destination commit, and several source
commits may map to the same one. The mapping is many-to-one and never remaps: a
source commit that already has a destination cannot be given a second.

Destination parents are computed by walking each source parent to its nearest
mapped ancestor, in parent order, keeping first occurrences. Parents outside the
replayed range contribute nothing, so a range bounded by an anchor does not drag
in history below it. When more than one mapped parent survives, any parent that
is already an ancestor of another is dropped.

If nothing maps and the epoch has a graft point, that graft point is the parent.

## Unchanged-tree collapse

A commit whose transformed tree equals its single destination parent's tree
writes no commit. It maps to that parent, and the run counts it as collapsed.
This is what makes upstream commits that touch nothing in the closure disappear
from generated history rather than accumulating as empty commits.

Collapse is checked rather than believed. A transformation that reports a change
while producing the baseline tree, or reports no change while producing a
different one, fails the run. The two claims have to agree.

A commit with no destination parent and no change maps to nothing at all.
Descendants then search further up, and the first one that changes becomes a
root.

## Merges

A source commit that resolves to two or more distinct destination parents is
always written, and the baseline is never consulted. A merge whose sides all
resolve to one destination commit is not a merge in the destination and
collapses like any ordinary commit.

## Commit shape

Every replayed commit:

1. preserves the upstream author name, email, and author date;
2. sets the bot as committer, with the upstream committer date;
3. keeps the upstream message and appends exactly one `Kubernetes-commit: <sha>`
   trailer;
4. is unsigned.

The trailer is appended onto an existing trailer block when there is one, or as
a new paragraph when there is not, and the result is re-parsed to confirm the
count and the last trailer are exactly what was intended. Committer dates come
from upstream rather than from a clock, so replay reads no clock at all.

## Release projection

At a selected source tag the engine computes an exact release projection: the
tree the module should have with real `v0.X.Y` staging dependencies rather than
the versions the replayed commit carries.

If the projection equals the replayed commit's tree, no commit is written and
the tag names the replayed commit directly. Otherwise exactly one synthetic
commit is written on top, with the bot as both author and committer, and a
message of the deterministic `Update dependencies to <tag>` shape that Kubernetes
staging repositories use. That commit carries no trailer and is verified after
writing: tree, single parent, both identities, byte-identical message, zero
trailers, unsigned.

The destination tag is annotated, maps `v1.X.Y[-pre]` to `v0.X.Y[-pre]`, and
uses the upstream tagger's timestamp. Its message is the destination tag name, a
blank line, and a trailer-only paragraph:

```text
v0.36.1

Source-tag: v1.36.1
Source-commit: <sha>
Source-release: https://github.com/kubernetes/kubernetes/releases/tag/v1.36.1
```

The tag is written and then peeled and compared against the object it was meant
to name.

## Publication

Refs are split into two scopes, and they never travel in one push.

| Scope | Refs | Why |
|---|---|---|
| Non-consumer | the state ref, progress refs | Engine bookkeeping. Nothing outside the engine reads them. |
| Consumer | the branch, the release tag | A module user or the Go module proxy can observe them. |

Non-consumer refs are pushed first. A failure between the two halves leaves a
resumable state rather than an unaccounted release.

The rules the publisher enforces:

1. A ref update that would recreate an existing tag with the same object is a
   no-op. One that would point an existing tag somewhere else is fatal.
2. A branch update must be a fast forward, proved locally and re-proved
   immediately before the push.
3. There is no force API. A `+`-prefixed refspec, an empty new object, and the
   all-zero null object are all rejected, so nothing can force or delete.
4. The push is atomic and carries a lease per ref, where an empty lease means
   "must not exist".
5. The remote is re-read before pushing and refused if any ref moved since
   planning, and re-read after pushing so an unapplied ref is an error even when
   the push reported success.
6. Repository configuration is queried for `url.*.insteadOf`,
   `url.*.pushInsteadOf`, and `remote.*.pushurl`, and a rewritten remote fails
   closed.

Namespaces are checked too: branches under `refs/heads/`, tags under
`refs/tags/`, the state ref at exactly its configured path, progress refs under
their configured prefix, and a branch update naming the state ref is refused.

## State

The state record is one JSON document, `state.json`, stored as a blob, tree, and
commit — writing it moves no ref. It holds:

```text
schema, objectFormat,
destination { repository, module },
anchor      { source, ref },
epoch       { profile, source, destination },
cursors[]   { ref, source, destination },
mapping     { digest, object, entries },
tracks[]    { name, ref, source, destination, done, total },
published[] { ref, kind, object, source },
engine      { version, toolchain },
digest
```

Decoding is strict, rejects trailing data, and then requires the input to be
byte-identical to the canonical re-render, so a record that was edited by hand
is not merely invalid but detectably so.

Merging a new record over a previous one enforces the append-only rules at the
record level rather than only at the push:

- object format, destination repository and module, and the anchor are immutable;
- within one epoch, cursors advance on both sides; across an epoch change, only
  the source side must descend;
- no cursor may be dropped, and mapping entry counts never fall;
- a track may disappear only when it is complete, and `done` and `total` never
  fall;
- a published branch must fast forward on both object and source;
- a published tag is compared for equality on object and source under every
  condition, including a profile change, and may never be dropped.

## Implemented pipeline

Replay, projection, publication, recovery, and state are integrated and tested
against real temporary repositories:

1. **Relevant DAG replay.** Each range is bounded by the recorded source position
   and pending release. A directory-granular watched set prefilters unrelated
   commits; relevant commits are generated at their exact OIDs. Merge parents are
   preserved and unchanged trees collapse.
2. **Intermediate dependency resolution.** Source commits map through bounded
   staging publishing histories. The Go command names pseudo-versions; Soapbox
   neither invents them nor fetches arbitrary object names.
3. **Resumable chunks.** Long ranges advance state and
   `refs/soapbox/progress/<release>` in non-consumer atomic pushes. The reachable
   mapping blob, digest, and entry count restore the exact version index after a
   restart. Consumer refs move only after the completed range passes release
   gates.
4. **Profile epoch grafting.** A changed output profile begins a new epoch on the
   verified current control-plane head. Earlier immutable tags are never
   regenerated.
5. **Authenticated network publication.** Destination refs and state are read
   over HTTPS, writes use the repository-scoped job `GITHUB_TOKEN`, and source Git
   plus Go subprocesses remain credential-free. Every push is atomic,
   fast-forward-only, and compare-and-swap leased.
6. **Crash reconciliation and fixed points.** State records both consumer branch
   and tag observations. A crash after consumer publication is adopted only after
   exact tag, provenance, cursor, and completed-track proof. Repeated runs
   converge to no generation or ref movement.

## Kubernetes patch staging topology

Adjacent staging tags may diverge from one another only under one accepted
shape: the previous tag sits exactly one unmerged, unclaimed dependency-update
commit above the unique merge base of the two tags. The current tag's
first-parent walk must begin at that base. Same-target tags (both names resolve
to the same object) and strictly linear histories between tags are accepted
without further proof.

All other topologies are refused:

- An absent or ambiguous merge base between adjacent tags.
- A spur above the base that contains more than one commit, any merge commit,
  or any `Kubernetes-commit` source claim.
- A current-tag ancestry that does not reach the base through first-parent
  links.

There is no lineage union and no fallback. A refused topology is fatal for the
release that requires it; earlier accepted releases are unaffected.

A legacy state record whose immutable anchor is the first patch release can only
prove that release's minor line. Discovery therefore ignores later minor tags
until a separately approved transition provides a common source anchor; tags in
the anchored line remain fail-closed. Repository creation and vanity-page
publication remain one-time outward bootstrap actions rather than sync behavior.
